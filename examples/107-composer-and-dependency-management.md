# 107 - Composer and dependency management: Example

## Goal

Create a small PHP command-line project that declares a runtime dependency, installs it with Composer, uses its generated autoloader, and keeps the manifest and lock file in Git.

## Question

How can a PHP project add a logging library in a controlled way, load its classes without manual `require` statements for each package file, and make future installs reproducible?

## Assumptions

- PHP 8.1 or newer is available on the command line.
- Composer is installed and available as `composer`.
- The example uses Monolog 3 as a runtime dependency.
- The commands are shown for a shell in the project directory; adapt path commands to your operating system.
- This example demonstrates dependency management and package loading. It does not configure a web server.

## 1. Create the project files

Make a directory named `composer-demo`, move into it, and create this `composer.json`:

~~~json
{
    "name": "example/composer-demo",
    "type": "project",
    "description": "A small PHP project that demonstrates Composer dependencies",
    "require": {
        "php": "^8.1",
        "monolog/monolog": "^3.0"
    }
}
~~~

The `require` section declares both the minimum PHP compatibility range and the runtime package. The caret constraint permits compatible Monolog 3 releases below 4.0. The exact version selected for this project will be recorded in the lock file.

Create a `.gitignore` file:

~~~gitignore
/vendor/
~~~

Composer generates the `vendor/` directory. Git should track the dependency manifest and lock file rather than the generated package copies.

## 2. Resolve and install dependencies

From the project root, run:

~~~sh
composer install
~~~

Because this new project does not yet have `composer.lock`, Composer resolves versions that satisfy the manifest, writes the lock file, and installs the packages under `vendor/`.

Validate the project metadata and inspect what Composer installed:

~~~sh
composer validate
composer show --direct
composer check-platform-reqs
~~~

`check-platform-reqs` checks the real PHP runtime and installed extensions. Run it in the same kind of environment that will execute the application.

## 3. Add a PHP script that uses the dependency

Create `src/run.php`:

~~~php
<?php

declare(strict_types=1);

require dirname(__DIR__) . '/vendor/autoload.php';

use Monolog\Handler\StreamHandler;
use Monolog\Level;
use Monolog\Logger;

$logger = new Logger('demo');
$logger->pushHandler(
    new StreamHandler('php://stderr', Level::Info)
);

$logger->info('Composer dependency loaded', [
    'package' => 'monolog/monolog',
]);
~~~

Composer's generated `vendor/autoload.php` makes the installed package classes available. The application does not need to locate or include Monolog source files individually.

Run the script:

~~~sh
php src/run.php
~~~

## Expected output

The message is written to standard error by the configured handler. Monolog includes a timestamp, so its exact value changes each time:

~~~text
[timestamp] demo.INFO: Composer dependency loaded {"package":"monolog/monolog"} []
~~~

The timestamp and formatting can vary with the installed Monolog version and handler formatter. The important result is that the `demo` logger emits an `INFO` message and includes the package context.

## 4. Understand the project state

After `composer install`, the relevant files and directories are:

~~~text
composer-demo/
├── .gitignore
├── composer.json
├── composer.lock
├── src/
│   └── run.php
└── vendor/                  generated; ignored by Git
    └── autoload.php         generated by Composer
~~~

For an application, commit `composer.json`, `composer.lock`, `.gitignore`, and the PHP source. Do not commit `vendor/` in this workflow. A fresh checkout can recreate it with `composer install`.

## 5. Repeat the install from the lock file

When the lock file exists, remove the generated `vendor/` directory locally if you want to simulate a fresh setup, then run:

~~~sh
composer install
~~~

Composer installs the exact versions recorded by `composer.lock`, as long as the current PHP and extension requirements are satisfied. Do not delete the committed lock file to get a clean install.

For a production deployment that does not need development packages, use the project's build or release process to run:

~~~sh
composer install --no-dev --prefer-dist --no-interaction
~~~

Monolog remains installed because it is declared in `require`, not `require-dev`.

## 6. Update dependencies deliberately

To resolve a newer Monolog version allowed by the constraint, run this during a planned update:

~~~sh
composer update monolog/monolog
~~~

Composer may also update related packages. Review the complete `composer.json` and `composer.lock` diff, run the project's checks, and commit the reviewed lock-file change. Deployment should then use `composer install` from that committed lock file.

To check available updates and known dependency findings, run:

~~~sh
composer outdated
composer audit
~~~

These commands report information; they do not replace reviewing an update and verifying that the application still behaves correctly.

## 7. Example Git workflow

A typical application commit includes:

~~~sh
git add composer.json composer.lock .gitignore src/run.php
git commit -m "Add Composer-managed logging dependency"
~~~

The generated `vendor/` directory is omitted because `.gitignore` excludes it. Composer credentials for private repositories should be provided through protected configuration, never committed with these files.

## What this example demonstrates

1. `composer.json` declares direct package and PHP requirements.
2. `composer install` creates `composer.lock` when one does not exist and installs packages.
3. `composer.lock` preserves the resolved versions for an application.
4. `vendor/` is generated and ignored in this project workflow.
5. `vendor/autoload.php` loads classes from installed dependencies.
6. Runtime packages belong in `require` so production installs retain them.
7. `composer update` is an intentional dependency change; deployment uses `composer install`.
8. Platform checks should run against the target PHP environment.
9. Audit and outdated reports are inputs to maintenance, not automatic fixes.

## Important notes

- Review a dependency's identity, maintenance, compatibility, license, and security information before adding it.
- Composer plugins and project scripts can execute code during dependency operations. Review them and grant plugin permission deliberately.
- `config.platform` can affect dependency resolution but does not install a PHP version or extension.
- Avoid `--ignore-platform-reqs` as a routine workaround; it hides a mismatch rather than resolving it.
- Keep credentials for private repositories out of source control, shell history, and logs.
- The PHP source in this example is provided for study and was not executed here.
