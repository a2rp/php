# 108 - Composer autoloading and PSR-4

## Goals

After this lesson, you should be able to:

- Explain what a PHP autoloader does.
- Load Composer's generated autoloader from an application entry point.
- Map a namespace prefix to one or more source directories with PSR-4.
- Match namespaces, directory names, and PHP file names correctly.
- Separate application autoloading from development-only autoloading.
- Regenerate Composer's autoloader when its configuration changes.
- Diagnose common class-not-found and case-sensitivity problems.
- Choose between PSR-4, classmap, and file autoloading for an appropriate use case.

## What autoloading solves

A PHP class must be defined before code can use it. Without an autoloader, a project may manually include every class file with `require` or `require_once` statements. As the application grows, those includes become difficult to maintain and easy to forget.

PHP's autoloading mechanism lets code ask an autoloader to load a class when that class is first needed. Composer builds an autoloader from the rules in `composer.json` and writes generated files under `vendor/`.

PHP's SPL autoload mechanism, exposed through `spl_autoload_register()`, lets libraries register callbacks for classes that are requested but not yet defined. Composer registers its generated loader through this mechanism, so an application normally includes Composer's loader instead of writing a separate callback.

A normal application entry point loads Composer's generated autoloader once:

~~~php
require __DIR__ . '/../vendor/autoload.php';
~~~

The exact relative path depends on where the entry point is located. The path above assumes the PHP file is inside a directory one level below the project root.

After the autoloader is included, application code can refer to classes from packages and from configured project namespaces without manually requiring each class file.

## Namespaces and fully qualified class names

A namespace groups related PHP declarations and helps distinguish classes with the same short name.

~~~php
<?php

namespace App\Service;

class Greeting
{
    public function message(string $name): string
    {
        return 'Hello, ' . $name . '!';
    }
}
~~~

The class's fully qualified name is `App\Service\Greeting`. A file using that class may import it with `use`:

~~~php
<?php

use App\Service\Greeting;

$greeting = new Greeting();
echo $greeting->message('Mira');
~~~

The `use` statement gives the code a shorter name to write. It does not load the file by itself; Composer's autoloader resolves the class when the code needs it.

## PSR-4 mapping

PSR-4 maps a namespace prefix to a directory. The namespace segments after the mapped prefix correspond to directories below that mapping, and the class name corresponds to a PHP file.

For example, map the `App\` prefix to `src/`:

~~~json
{
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    }
}
~~~

In JSON, each backslash is escaped. The key above represents the PHP namespace prefix `App\` with its final namespace separator included.

With this mapping, the fully qualified class `App\Service\Greeting` is looked up at:

~~~text
src/Service/Greeting.php
~~~

That file should declare the matching namespace and class:

~~~php
<?php

namespace App\Service;

class Greeting
{
    // Class implementation
}
~~~

The `App\` prefix itself is not repeated as a directory name beneath `src/`. The remaining namespace, `Service`, becomes the directory path.

### PSR-4 naming rules to follow

- A namespace prefix in Composer's mapping should end with `\` to avoid accidental matches with longer prefixes.
- Namespace segments after the prefix map to directories below the mapped base directory.
- The class name maps to a file ending in `.php`.
- Keep namespace, directory, and file-name case consistent.
- The mapped path is relative to the package root, normally the directory containing `composer.json`.
- Use forward slashes in Composer path values; they work across supported operating systems.

A class might appear to load on a case-insensitive filesystem even when a directory or file has the wrong capitalization. Linux and other case-sensitive environments can then report a class-not-found error. Match the declared names and file paths exactly.

## A more complete project layout

A small project can use this structure:

~~~text
my-app/
├── composer.json
├── public/
│   └── index.php
├── src/
│   └── Service/
│       └── Greeting.php
├── tests/
│   └── Service/
│       └── GreetingTest.php
├── composer.lock
└── vendor/                 generated by Composer
    └── autoload.php        generated by Composer
~~~

The `public/index.php` entry point loads `vendor/autoload.php` using a path based on `__DIR__`. Composer then finds classes under `src/` using the configured PSR-4 rule.

## Configure a project's namespace

Add an `autoload` mapping to the project's existing `composer.json`:

~~~json
{
    "name": "example/my-app",
    "type": "project",
    "require": {
        "php": "^8.1"
    },
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    }
}
~~~

After adding or changing autoload configuration, regenerate Composer's autoloader:

~~~sh
composer dump-autoload
~~~

This command reads the current Composer configuration and rebuilds generated autoload files. Do not edit files inside `vendor/composer/` by hand; Composer may replace them the next time it runs.

Once the mapping is configured, adding a class under the already mapped directory normally does not require another dump in a standard development setup. Composer's PSR-4 loader can locate the class when it is requested. If the mapping or other autoload configuration changes, regenerate the autoloader.

## Load the application autoloader

For `public/index.php`, the project root is its parent directory:

~~~php
<?php

declare(strict_types=1);

use App\Service\Greeting;

require dirname(__DIR__) . '/vendor/autoload.php';

$greeting = new Greeting();
echo $greeting->message('Mira');
~~~

The order matters: include the Composer autoloader before code tries to instantiate an autoloaded class. `dirname(__DIR__)` makes the path relative to the script location rather than the current working directory.

Expected output:

~~~text
Hello, Mira!
~~~

## Multiple directories for one prefix

A namespace prefix can point to more than one directory:

~~~json
{
    "autoload": {
        "psr-4": {
            "App\\": ["src/", "legacy-src/"]
        }
    }
}
~~~

Composer checks the configured locations for a matching class file. Prefer one clear source directory for a new project; use multiple locations only when there is a real organizational need.

More specific namespace prefixes can have their own mapping. For instance, a library may map its main namespace to `src/` and a separate namespace to a compatibility directory. Keep mappings explicit and avoid overlapping prefixes without a reason.

## Development-only classes with `autoload-dev`

A root project can configure classes used only for tests or development tools with `autoload-dev`:

~~~json
{
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "App\\Tests\\": "tests/"
        }
    }
}
~~~

A test class under `tests/Service/GreetingTest.php` would declare `App\Tests\Service` as its namespace.

`autoload-dev` belongs to the root project configuration. It is intended for classes needed by that project's tests and development. It should not expose test classes as part of the package's runtime autoload rules. Production installs that omit development dependencies also omit development-only autoload rules.

## Other Composer autoload modes

PSR-4 is the normal choice for new namespaced PHP classes. Composer also supports other mechanisms for specific situations.

### Classmap

A classmap tells Composer to scan specified files or directories for class-like declarations and generate a lookup map:

~~~json
{
    "autoload": {
        "classmap": ["legacy/"]
    }
}
~~~

Classmaps can help integrate legacy code that does not follow a predictable PSR-4 directory layout. Regenerate the autoloader after adding classes to a classmapped directory so the generated map includes them.

### Files

The `files` mechanism includes listed PHP files when Composer's autoloader is loaded:

~~~json
{
    "autoload": {
        "files": ["src/legacy-functions.php"]
    }
}
~~~

This is useful for functions or legacy code that cannot be loaded by requesting a class name. Included files run code at load time, so avoid unnecessary side effects. Do not use `files` as a substitute for PSR-4 class loading.

### Legacy PSR-0

Composer supports PSR-0 for older packages. New code should generally use PSR-4, which provides a clearer namespace-to-directory mapping without including the namespace prefix as a directory path under the mapped base directory.

## Development and production autoloader options

For most local development, the regular generated autoloader is sufficient. Composer also has optimization options for production builds:

~~~sh
composer dump-autoload --optimize
~~~

Optimization can build a class map from discoverable classes to reduce filesystem lookups. It is a build-time optimization; regenerate it when the source or autoload configuration changes.

The authoritative classmap option restricts loading to classes known to the generated class map. It can improve lookup behavior in controlled deployments, but classes added after generation will not be discovered through normal PSR-4 fallback. Use it only when the production build process generates the class map from the complete deployed source tree.

Do not commit generated autoloader internals or rely on editing them manually. The project configuration is the source of truth.

## Troubleshooting class-not-found errors

When Composer cannot load a class, check these items in order:

1. The application included the correct `vendor/autoload.php` file before using the class.
2. `composer.json` contains the intended PSR-4 prefix and base directory.
3. The namespace prefix ends with a separator and is spelled correctly.
4. The PHP namespace declaration matches the class's fully qualified name.
5. The directory segments and `.php` file name match the namespace and class name, including capitalization.
6. The mapped paths are relative to the correct package root and the file is actually inside the expected directory.
7. Composer configuration is valid and the autoloader was regenerated after a mapping change.
8. The class is not confined to `autoload-dev` while being requested in a production install.
9. The source file declares the expected class, interface, trait, or enum.
10. A custom optimization or authoritative classmap was generated after the latest source files were added.

If the problem remains, inspect the mapping and filesystem path first. Adding a manual `require` can hide a broken namespace rule and make the project harder to maintain.

## Common mistakes

### Omitting the trailing namespace separator

Mapping `App` instead of `App\` can match unintended namespace prefixes. Include the separator in the mapping key.

### Repeating the namespace prefix in the directory structure

If `App\` maps to `src/`, then `App\Service\Greeting` maps to `src/Service/Greeting.php`, not `src/App/Service/Greeting.php`.

### Loading the wrong autoloader path

A path relative to the current shell directory may work in one command and fail in another. Build the path from `__DIR__` or `dirname(__DIR__)` based on the source file's location.

### Relying on case-insensitive local behavior

Use exactly the same capitalization for the namespace, directory names, and PHP file name. Verify on a case-sensitive environment when possible.

### Forgetting to regenerate after changing Composer configuration

After changing PSR-4, classmap, or file mappings, run `composer dump-autoload` and inspect errors or warnings.

### Putting tests in production autoload rules

Use `autoload-dev` for root-project test classes so they are not part of ordinary package runtime autoloading.

### Using `files` to load every class

Use PSR-4 for classes. Reserve `files` for functions or compatibility code that cannot be autoloaded by class name.

### Editing generated vendor files

Make changes in `composer.json` and source files, then regenerate. Files under `vendor/` are generated and can be overwritten.

## Key takeaways

- Include `vendor/autoload.php` once before using Composer-managed classes.
- A PSR-4 mapping connects a namespace prefix to a directory relative to the package root.
- The remaining namespace segments and class name determine the subdirectory and `.php` file.
- Keep the prefix separator, namespace, and filesystem capitalization consistent.
- Use `autoload-dev` for root-project test classes and keep runtime classes in `autoload`.
- Run `composer dump-autoload` after changing autoload configuration.
- Use classmap for legacy layouts and `files` sparingly for functions or compatibility code.
- Production autoloader optimization should be generated from the complete deployed source tree.
- Fix the namespace-to-path mapping instead of accumulating manual includes.
