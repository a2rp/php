# 092 - Password hashing and verification

## Learning goals

By the end of this lesson, you will be able to:

- Explain why passwords must be stored as one-way password hashes rather than plaintext or reversible encryption.
- Create a password hash with `password_hash()` and check it with `password_verify()`.
- Store the complete hash string, including its algorithm metadata and salt.
- Upgrade older hashes after a successful login with `password_needs_rehash()`.
- Avoid fast general-purpose hashes, manual salts, and silent password truncation.
- Place password hashing in a larger registration and login flow.

## 1. Store a hash, never the original password

A server needs to compare a submitted password with the credential created at registration. It should not need to recover the original password. Store a purpose-built password hash, not plaintext and not a reversibly encrypted password.

A password hash is produced by a one-way, deliberately expensive algorithm. Each user should have a distinct salt, generated by the password-hashing API. The hash output includes the algorithm information and salt needed to verify it later.

Do not use fast general-purpose hashes such as MD5 or SHA-1 for passwords. They are designed to calculate quickly, which also lets attackers test many guesses quickly if a database is stolen.

## 2. Create a hash with `password_hash()`

```php
<?php

$password = 'a-long-example-passphrase';
$hash = password_hash($password, PASSWORD_DEFAULT);
```

`PASSWORD_DEFAULT` selects PHP's current default password-hashing algorithm. That default can change as PHP adopts stronger algorithms, so allow enough room for the result to grow. A database field such as `VARCHAR(255)` is a practical size for storing password hashes.

Do not provide your own salt. PHP generates a suitable random salt and embeds the necessary salt and algorithm information in the returned hash. Do not use a constant, username, or `rand()`-generated value as a salt.

Supported algorithms depend on the PHP build. Argon2id can be used when PHP has been built with Argon2 support; test its availability and tune its resource costs on the actual deployment hardware before selecting it.

## 3. Verify with `password_verify()`

During login, fetch the stored hash for the account and verify the submitted password against it:

```php
if (password_verify($submittedPassword, $storedHash)) {
    // The supplied password matches this stored hash.
} else {
    // The supplied password does not match.
}
```

`password_verify()` reads the algorithm and salt information from the stored hash and performs a timing-safe verification. Do not try to recreate a hash and compare strings with `===`; password hashing uses a random salt, so repeated hashes of the same password are normally different.

The stored hash is not an encrypted password and there is no decryption step. The user proves knowledge of the password by submitting a candidate that verifies against the hash.

## 4. Upgrade hashes after successful verification

Hashing algorithms and cost settings can change. After a password has been verified, check whether its stored hash matches the current policy:

```php
$algorithm = PASSWORD_DEFAULT;
$options = [];

if (password_verify($submittedPassword, $storedHash)) {
    if (password_needs_rehash($storedHash, $algorithm, $options)) {
        $newHash = password_hash($submittedPassword, $algorithm, $options);
        // Replace the stored hash with $newHash using a prepared database query.
    }

    // Continue the successful login flow.
}
```

Rehash only after verification succeeds. The application has the plaintext candidate for that request at this point, so it can create a new hash and replace the old stored value. Never store or log the submitted password during this process.

## 5. Registration and login flow

### Registration

1. Read the submitted password as a string and apply the application's length policy without silently truncating it.
2. Hash it with `password_hash()`.
3. Store the returned hash in a sufficiently wide database column, along with the account's other required data.
4. Do not store a separate salt; the password hash already contains what verification needs.

The database write should use a prepared statement. For example, after validating the account fields and creating `$hash`:

```sql
INSERT INTO users (email, password_hash)
VALUES (:email, :password_hash)
```

### Login

1. Find the account using a normalized identifier and a prepared query.
2. Fetch its stored `password_hash`.
3. Pass the submitted password and stored hash to `password_verify()`.
4. If verification succeeds, rehash when `password_needs_rehash()` says the current policy has changed.
5. Continue authentication only after all required checks succeed.

Return a generic failure such as “Invalid email or password” so the response does not reveal whether an account exists. Apply rate limits and monitoring to repeated login attempts; password hashing alone does not stop online guessing.

## 6. Password length and algorithm limits

Do not silently trim or truncate passwords. A maximum input size can help bound request and hashing work, but choose it deliberately, document it, and apply the same policy during registration, login, and password changes.

If an application explicitly selects bcrypt with `PASSWORD_BCRYPT`, be aware that bcrypt processes at most 72 bytes of a password. Bytes are not the same as visible characters for multibyte text. Avoid silently accepting two different long inputs as equivalent. `PASSWORD_DEFAULT` may use another algorithm in a future PHP release, so do not assume every default algorithm has the same input limit.

Use a password field that lets users use long passphrases and password managers. Avoid arbitrary composition rules that force predictable changes; enforce the application's documented policy and protect the authentication endpoint with rate limiting and other appropriate controls.

## 7. Important boundaries

- **Hashing is not encryption.** The application should not be able to recover a user's password.
- **Salt is not a secret.** It is unique per hash and stored with it; the password API handles generation.
- **Hashing is not rate limiting.** Expensive hashes slow offline guesses but do not prevent many online login attempts.
- **A hash is not an authentication flow.** Account verification, session creation, authorization, recovery, and monitoring have their own requirements.
- **Never log credentials.** Avoid logging passwords, reset tokens, or complete authentication request bodies.
- **Keep database access parameterized.** Hashing does not prevent SQL injection.

## Common mistakes

### Saving plaintext

```php
// Wrong: storing the original password in the database.
$databaseRow['password'] = $submittedPassword;
```

Store the output of `password_hash()` instead.

### Using a fast hash or encryption as password storage

```php
// Wrong for password storage.
$hash = md5($submittedPassword);
```

Use PHP's password hashing API. Do not design a custom password hashing scheme.

### Generating a manual salt

```php
// Wrong: do not generate or pass a custom salt.
$hash = password_hash($submittedPassword, PASSWORD_DEFAULT, [
    'salt' => 'same-value-for-everyone',
]);
```

Let `password_hash()` generate a random salt automatically.

### Comparing newly generated hashes as strings

```php
// Wrong: password_hash() uses a random salt.
if (password_hash($candidate, PASSWORD_DEFAULT) === $storedHash) {
    // ...
}
```

Use `password_verify($candidate, $storedHash)`.

## Key takeaways

- Use `password_hash()` to create hashes and `password_verify()` to check them.
- Store the complete returned hash in a column large enough for future algorithms, commonly `VARCHAR(255)`.
- Let PHP generate the salt; never store plaintext passwords or use a fast general-purpose hash.
- After a successful verification, use `password_needs_rehash()` to migrate to current parameters.
- Do not silently truncate passwords, and remember bcrypt's 72-byte limit if explicitly choosing bcrypt.
- Combine password hashing with prepared queries, rate limiting, generic login errors, and a secure authentication flow.
