# 107 - Composer and dependency management: Q&A

## Multiple-choice questions

### 1. What is Composer primarily used for in a PHP project?

- **A.** Managing PHP package requirements and installing dependencies
- **B.** Replacing the PHP interpreter
- **C.** Automatically creating database tables
- **D.** Serving HTTP requests

**Answer: A.** Composer resolves package requirements and installs dependencies. **Explanation:** It does not replace PHP itself, a web server, or an application framework.

### 2. What does a project's `composer.json` primarily describe?

- **A.** Direct requirements, constraints, and Composer project metadata
- **B.** The exact installed file contents of every package
- **C.** The server's PHP configuration at runtime
- **D.** Only packages that are installed globally

**Answer: A.** `composer.json` declares what the project directly requires and may contain other project metadata. **Explanation:** The resolved package versions are recorded in `composer.lock`.

### 3. For an application, why should `composer.lock` normally be committed?

- **A.** It records the resolved package versions so installs can reproduce that dependency set
- **B.** It replaces `composer.json`
- **C.** It contains the application's source code
- **D.** It prevents every future dependency update

**Answer: A.** The lock file records exact resolved versions, including transitive dependencies. **Explanation:** `composer install` can use it so developers, CI, and deployment use the same selected versions, subject to platform compatibility.

### 4. What does `composer install` do when a lock file is present?

- **A.** Installs the versions recorded in the lock file
- **B.** Always upgrades every package to the newest release
- **C.** Deletes the project's direct requirements
- **D.** Installs only development packages

**Answer: A.** With a lock file, install uses its resolved package versions. **Explanation:** If no lock file exists, Composer resolves the manifest requirements and creates a lock file.

### 5. When should an application normally run `composer update`?

- **A.** When intentionally resolving newer versions allowed by the constraints
- **B.** On every production request
- **C.** Whenever `composer install` finishes successfully
- **D.** Before checking out the project files

**Answer: A.** Update deliberately resolves versions again and changes the lock file. **Explanation:** Review and commit the resulting manifest and lock changes; deployment normally installs from that lock file.

### 6. Where should a package used by production application code be declared?

- **A.** `require`
- **B.** `require-dev` only
- **C.** `autoload-dev` only
- **D.** The global Composer configuration

**Answer: A.** Runtime packages belong in `require`. **Explanation:** A production install using `--no-dev` omits `require-dev` packages.

### 7. What is normally the right Git treatment for `vendor/` in an application?

- **A.** Ignore it and install it from the committed Composer files
- **B.** Commit it instead of `composer.lock`
- **C.** Edit all package files directly in it
- **D.** Rename it to `composer.json`

**Answer: A.** `vendor/` is generated by Composer and is normally ignored. **Explanation:** Commit `composer.json` and `composer.lock` so each environment can install the selected dependencies.

### 8. What is a transitive dependency?

- **A.** A package required by another package in the dependency graph
- **B.** A package that is never installed
- **C.** A package installed only by PHP's interpreter
- **D.** A dependency that must always be listed in `require-dev`

**Answer: A.** A transitive dependency is brought in because another package requires it. **Explanation:** Declare a package directly when your own code uses it, even if another dependency currently brings it in.

### 9. For a nonzero major version, what does a typical constraint such as `^3.0` allow?

- **A.** Compatible releases from 3.0.0 up to, but not including, 4.0.0
- **B.** Only version 3.0.0 exactly
- **C.** Every release from 0.0.0 onward
- **D.** Only releases with an even minor number

**Answer: A.** A caret constraint allows compatible releases without crossing the next breaking major boundary for a nonzero major version. **Explanation:** Caret constraints have special behavior for `0.x`, so inspect the actual range instead of assuming the same boundary in every case.

### 10. What does `composer check-platform-reqs` help verify?

- **A.** Whether the actual PHP runtime and extensions satisfy installed package requirements
- **B.** Whether every package has a permissive license
- **C.** Whether a Git remote is reachable
- **D.** Whether the HTML pages render correctly

**Answer: A.** The command checks platform requirements against the PHP environment in which it runs. **Explanation:** Run it in the target runtime or deployment image; a local machine may have different extensions.

### 11. What does `composer audit` do?

- **A.** Checks dependency data against available security advisories and dependency policies
- **B.** Automatically upgrades all vulnerable packages without changing the lock file
- **C.** Encrypts credentials in `composer.json`
- **D.** Proves that every dependency is safe

**Answer: A.** Audit reports known advisory and policy findings for the dependency set. **Explanation:** It does not update packages or prove that no unknown risk exists; investigate findings and plan appropriate changes.

### 12. What is the purpose of Composer's `allow-plugins` configuration?

- **A.** To control which Composer plugins are permitted to execute
- **B.** To choose the PHP version used by a web server
- **C.** To add every package as a plugin
- **D.** To disable `composer.lock`

**Answer: A.** Composer plugins can execute code, so projects can explicitly allow the plugins they trust. **Explanation:** Review plugin identity and purpose before granting permission.

## Short-answer questions

### 13. What is the difference between `composer.json` and `composer.lock`?

**Answer:** `composer.json` declares direct package requirements and version constraints; `composer.lock` records the exact resolved versions for the project. **Explanation:** The manifest describes the allowed dependency set, while the lock file records one selected set for reproducible application installs.

### 14. What happens when `composer install` runs without an existing lock file?

**Answer:** Composer resolves versions that satisfy `composer.json`, installs them, and creates `composer.lock`. **Explanation:** Review and commit the generated lock file for an application so later installs can use the same resolution.

### 15. How do you add a package needed only for local development and tests?

**Answer:** Use `composer require --dev vendor/package`. **Explanation:** Composer records it under `require-dev`, which a production install can omit with `--no-dev`.

### 16. Why is `composer update` different from `composer install`?

**Answer:** `update` resolves package versions again within the declared constraints and changes the lock file; `install` uses the lock file when available. **Explanation:** Use update for planned dependency changes, and install for a repeatable setup or deployment.

### 17. Why can a targeted `composer update package/name` change more than one lock-file entry?

**Answer:** Composer may need to update related dependencies to satisfy the selected package's requirements. **Explanation:** Inspect the whole lock-file diff; the named package is not guaranteed to be the only changed package.

### 18. Why should code declare a package directly if it uses that package's API?

**Answer:** The code should not rely on another package to bring in its own dependency transitively. **Explanation:** If the intermediary package changes or is removed, an undeclared dependency may disappear and break the application.

### 19. Does `config.platform` install or emulate a different PHP runtime?

**Answer:** No. It influences dependency resolution as if the configured platform were present. **Explanation:** It does not install PHP or extensions; verify the real runtime with platform checks.

### 20. Why should `--ignore-platform-reqs` not be a routine workaround?

**Answer:** It suppresses compatibility checks without making the installed runtime compatible. **Explanation:** A package may still fail when it calls a missing extension or unsupported PHP feature.

### 21. What should an application normally commit and ignore for Composer dependencies?

**Answer:** Commit `composer.json` and `composer.lock`; normally ignore generated `vendor/`. **Explanation:** The manifest and lock file describe the dependency set, while Composer recreates installed package files.

### 22. Why can Composer plugins and scripts be security-sensitive?

**Answer:** They can execute code during Composer operations. **Explanation:** Review project scripts and package plugins before running Composer, and allow only plugins the project intentionally trusts.

### 23. What should you do with credentials for a private package repository?

**Answer:** Provide them through protected user-level configuration or a secured environment, and keep them out of source control. **Explanation:** Do not put active credentials in a committed manifest, example file, shell history, or logs.

### 24. What does `composer validate` check?

**Answer:** It validates Composer project metadata and can report whether the manifest and lock file are consistent. **Explanation:** Run it after dependency changes, then review the file diff as well.

## Practical and scenario questions

### 25. A new team member clones an application that contains both Composer files but no `vendor/` directory. What should they run?

**Answer:** Run `composer install` from the project root. **Explanation:** Composer reads the committed lock file and installs the resolved dependencies into `vendor/`, subject to the machine's platform requirements.

### 26. A deployment script runs `composer update` and production starts receiving different package versions from one release to the next. What should change?

**Answer:** Resolve and review updates in a controlled development or build workflow, commit the lock file, and deploy with `composer install`. **Explanation:** Updating during deployment can select newer allowed versions at deployment time and make releases inconsistent.

### 27. A package works on a developer's machine but fails in the production container because an extension is absent. What should the team check?

**Answer:** Check the package's `ext-*` requirement and run `composer check-platform-reqs` inside the production container or equivalent image. **Explanation:** A successful local install does not prove the target runtime has the same extensions.

### 28. An application uses a logger in production, but it was added with `composer require --dev`. What is the likely problem?

**Answer:** A production install with `--no-dev` will omit the logger package. **Explanation:** Move a dependency used by production code into `require` and update and review the lock file.

### 29. Your code calls a class from a package that appears in `composer.lock`, but your `composer.json` does not list it. What should you do?

**Answer:** Add the package as a direct requirement using Composer. **Explanation:** Its current presence may be only transitive, and another package could stop requiring it in a later update.

### 30. Composer reports that a dependency requires a higher PHP version than the deployment uses. Can `config.platform` or `--ignore-platform-reqs` make that code run safely?

**Answer:** No. Select compatible package versions or upgrade the actual deployment PHP version. **Explanation:** `config.platform` affects resolution, and `--ignore-platform-reqs` hides checks; neither supplies missing runtime features.

### 31. Installing a package prompts you to allow a Composer plugin you have never seen before. What is the safe next step?

**Answer:** Verify the package and plugin identity, inspect why it is needed, and allow it only if the project intentionally trusts it. **Explanation:** Plugins can execute code during Composer operations; do not approve an unfamiliar plugin automatically.

### 32. A developer commits a real repository token in a configuration file, then removes it in a later commit. Is the token safe now?

**Answer:** No. Revoke or rotate it and provision a replacement outside the repository. **Explanation:** The original value may remain in Git history, clones, caches, or logs; removing the latest copy does not undo exposure.

### 33. `composer audit` reports an advisory for a direct dependency. What should the team do next?

**Answer:** Read the finding, identify affected versions and available fixes, then update to a compatible version and review the lock-file changes. **Explanation:** Audit reports findings; it does not itself update or test the application.

### 34. A project commits `vendor/` but forgets `composer.lock`. Why is this workflow fragile?

**Answer:** The committed generated directory can become stale while there is no recorded resolution for a reproducible install. **Explanation:** Prefer committing the manifest and lock file, ignoring `vendor/`, and rebuilding dependencies with Composer.

### 35. A reusable library has its own `composer.lock`. Will that lock file choose package versions for every application that installs the library?

**Answer:** No. The consuming application resolves dependencies from package constraints in the library's manifest and its own lock file. **Explanation:** A library may keep its lock file for its own development and tests, but consumers do not inherit it as their dependency lock.

### 36. A package update changes several transitive dependencies as well as the requested package. Should the extra changes be discarded automatically?

**Answer:** No. Review why each package changed and whether the complete resolved set is compatible. **Explanation:** Composer may need related changes to satisfy constraints; test the resulting application before committing the update.
